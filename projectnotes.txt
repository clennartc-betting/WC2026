0. SAMENVATTING IN EEN ZIN
--------------------------------------------------------------------------------

Een volledig hands-off Python-script dat elke 6 uur draait via GitHub Actions,
odds voor WK 2026 wedstrijden ophaalt bij The Odds API, odds-bewegingen
analyseert, virtuele bets plaatst volgens een sharp/publiek-strategie met
quarter Kelly sizing, automatisch wedstrijden afwikkelt en alles rapporteert
via GitHub Issues.



--------------------------------------------------------------------------------
1. PROJECTDOEL
--------------------------------------------------------------------------------

Hobby-experiment: kan een betting-strategie gebaseerd op odds-beweging +
timing theoretisch winstgevend zijn op WK 2026 wedstrijden?

Beperkingen die we voor onszelf hebben opgelegd:
  - Alleen 1X2 / WDL op 90 minuten (drie uitkomsten: thuis, gelijkspel, uit).
  - GEEN echt geld; bets zijn virtueel.
  - Geen actieve betrokkenheid: het systeem draait, beslist en rapporteert
    zelfstandig. De gebruiker checkt enkel de GitHub Issues / stats.



--------------------------------------------------------------------------------
2. STRATEGIE
--------------------------------------------------------------------------------

Per scrape (elke 6 uur) berekenen we voor elke aankomende wedstrijd de
mediaan-odd over alle beschikbare bookmakers per uitkomst, en daarmee de
mediaan-implied-probability. Op deze geaggregeerde tijdreeks zoeken we
twee soorten signalen:

  (A) VROEG SHARP SIGNAAL
      Voorwaarde: in de fase TOT 48 uur voor aftrap is de implied
      probability van een uitkomst met >= 6%-punt OMHOOG bewogen.
      Interpretatie: sharps (professionele wedders) duwen deze lijn.
      Actie: bet op die uitkomst (meebewegen met de scherpe markt).

  (B) LAAT PUBLIEK SIGNAAL
      Voorwaarde: in de laatste 6 uur voor aftrap is de implied
      probability van een uitkomst met >= 6%-punt OMLAAG bewogen.
      Interpretatie: het publiek koopt de "andere kant" en duwt
      de prijs op deze uitkomst weg.
      Actie: bet op die uitkomst (fade het publiek).

Drempels en venster zijn allemaal configureerbaar via env-vars
(zie sectie 8 "Configuratie").


2.1  Bet-sizing - quarter Kelly
-------------------------------

Voor elk signaal schatten we de "echte" win-probability als:

   p_hat = min( implied_prob + |beweging| * confidence * 0.3 , 0.95 )

waarbij confidence = min(|beweging| / drempel, 2.0). Dat wil zeggen:
hoe groter de beweging t.o.v. de drempel, hoe meer we geloven in een
edge - tot maximaal 2x de drempel.

Kelly fractie:    f* = (p_hat * b - q) / b   waarbij b = odd - 1
Inzet:            stake = bankroll * f* * 0.25
Cap:              nooit > 5% van bankroll per bet (MAX_BET_FRACTIE)

We staken zowel tegen de "compound" bankroll (start EUR 100, groeit/krimpt
met resultaten) als tegen een vaste EUR 100 referentie. Beide getallen
worden per bet en in de stats apart bijgehouden, zodat je het effect van
compounding kunt vergelijken.


2.2  Re-bet regels
------------------

Re-bets ("middelen" op dezelfde edge als de beweging doorzet):

  - Per (wedstrijd, uitkomst): max 2 bets (1 initial + 1 re-bet).
  - Per wedstrijd: ALLEEN op die ene uitkomst waarop al een bet ligt.
    We staan dus geen tegengestelde bets op dezelfde wedstrijd toe.
  - Re-bet voorwaarde: huidige |beweging| >= 12% (re-bet drempel) EN
    dezelfde richting als de oorspronkelijke beweging.
  - Re-bet-stake gebruikt actuele bankroll en huidige odd op moment
    van triggeren (de odd wordt opnieuw "gelocked").

4B. SCHEDULING-BETROUWBAARHEID (waarom elke 2u + self-throttle)
--------------------------------------------------------------------------------

PROBLEEM (waargenomen 2026-06-06):
  De cron stond op '0 */6 * * *' (4x/dag). In de praktijk vuurde GitHub
  maar ~2x/dag, met vertragingen tot 6u en gaten tot ~20u. ALLE runs
  slaagden (geen fouten) - GitHub SLOEG scheduled slots simpelweg OVER.
  Dit is bekend, gedocumenteerd gedrag van GitHub Actions 'schedule' op
  de gratis tier, vooral op het hele uur (minuut :00 is het drukst).

OPLOSSING (twee delen):
  1) Over-schedulen: cron staat nu op '37 */2 * * *' = elke 2u op een
     'oneven' minuut (12 pogingen/dag i.p.v. 4). Meer pogingen = grotere
     kans dat er genoeg landen, ook als GitHub er veel overslaat.
  2) Self-throttle in het script (functie moet_scrapen): bij ELKE run
     beslist het script of het ECHT de Odds API aanroept, op basis van
     tijd sinds de laatste succesvolle scrape:
        - normaal:     minimaal WK2026_MIN_SCRAPE_GAP_HOURS (3.5u) ertussen
        - boost:       valt de eerstvolgende aftrap binnen
                       WK2026_SCRAPE_BOOST_WINDOW_HOURS (6u), dan mag het
                       elke WK2026_MIN_SCRAPE_GAP_BOOST_HOURS (1.5u).
     Zo blijft het credit-verbruik begrensd, ongeacht hoe vaak de
     workflow draait, EN krijgen we dichte datapunten vlak voor aftrap
     (nodig voor het 'laat_publiek' signaal).

GEVOLG VOOR DE FLOW:
  - Bet-evaluatie draait alleen als er ECHT gescraped is (nieuwe data).
  - Settlement (scores) en pre-match alerts draaien ELKE run, los van de
    scrape-throttle, zodat timing strak blijft.

WAT ALS HET NOG STEEDS TE WEINIG IS?
  GitHub kan ook elke-2u-slots overslaan. Mocht je echt strakke cadans
  willen, dan is de robuustste optie een EXTERNE trigger (bv. het gratis
  cron-job.org dat elke X min de 'workflow_dispatch' via de GitHub API
  aanroept). Niet ingebouwd; de over-schedule + throttle is voor dit
  hobby-doel ruim voldoende en voegt geen externe afhankelijkheid toe.

5. DATABASE-SCHEMA (SQLite, file: wk2026.db)
--------------------------------------------------------------------------------

  wedstrijden            <-- één rij per match
    id              TEXT  PK  (Odds-API event ID)
    thuisteam       TEXT
    uitteam         TEXT
    aanvang         TEXT  (ISO timestamp UTC)
    voltooid        INT   (0/1, 1 zodra /scores zegt completed=true)
    thuis_score     INT
    uit_score       INT
    winnaar         TEXT  ('thuis'/'gelijkspel'/'uit')
    afgewikkeld_op  TEXT
    gh_issue_number INT   (GitHub Issue nummer voor deze match)
    prematch_genotificeerd TEXT  (timestamp; NULL = nog geen alert gestuurd)

  odds_snapshots         <-- één rij per (scrape, bookmaker, uitkomst)
    id              INT PK
    wedstrijd_id    TEXT FK
    bookmaker       TEXT  (bv 'pinnacle', 'bet365', 'unibet')
    uitkomst        TEXT  ('thuis'/'gelijkspel'/'uit')
    odd             REAL  (decimal odd, bv 2.45)
    implied_prob    REAL  (1/odd, bv 0.4082)
    timestamp       TEXT  (ISO UTC; gelijk binnen één scrape)

  aggregated_snapshots   <-- één rij per (scrape, uitkomst) per match
    id              INT PK
    wedstrijd_id    TEXT FK
    uitkomst        TEXT
    median_odd      REAL  (mediaan over bookmakers)
    mean_odd        REAL  (gemiddelde over bookmakers)
    n_bookmakers    INT   (aantal samples in deze aggregatie)
    implied_prob    REAL  (1 / median_odd; gebruikt voor signalen)
    timestamp       TEXT

  bets                   <-- alle (virtuele) bets
    id                       INT PK
    wedstrijd_id             TEXT FK
    uitkomst                 TEXT
    signaal_type             TEXT  ('vroeg_sharp' / 'laat_publiek')
    beweging_prob            REAL  (de Delta die het signaal triggerde)
    locked_odd               REAL  (aggregated median odd op bet-moment)
    is_rebet                 INT   (0 of 1)
    stake_compound           REAL  (Kelly op compound bankroll)
    stake_fixed              REAL  (Kelly op vaste EUR 100 referentie)
    bankroll_compound_at_bet REAL  (snapshot voor traceability)
    payout_compound          REAL  (NULL tot settled)
    payout_fixed             REAL  (NULL tot settled)
    pnl_compound             REAL  (payout - stake)
    pnl_fixed                REAL
    resultaat                TEXT  ('gewonnen'/'verloren', NULL = open)
    geplaatst_op             TEXT
    afgewikkeld_op           TEXT

  api_runs               <-- audit log voor API gebruik
    id              INT PK
    timestamp       TEXT
    endpoint        TEXT  ('odds' / 'scores')
    credits_used    INT   (van header x-requests-used)
    credits_remaining INT (van header x-requests-remaining)
    status          TEXT  ('ok' / error message)

6. CLI COMMANDO'S
--------------------------------------------------------------------------------

  python wk2026_tracker.py daily-run
      Volledige cyclus: scrape + aggregate + beslis + settle + notify.
      Dit is wat GitHub Actions elke 6 uur draait.

  python wk2026_tracker.py scrape
      Alleen odds ophalen, ruw + aggregaat opslaan. Geen bets/notify.

  python wk2026_tracker.py signalen
      Toon alle huidige signalen voor aankomende wedstrijden (read-only).
      Handig om de strategie-output te bekijken zonder bets te plaatsen.

  python wk2026_tracker.py beslis
      Plaats virtuele bets op basis van actuele signalen + notificeer.
      Equivalent aan stappen 4-5 van daily-run.

  python wk2026_tracker.py settle
      Haal /scores op, wikkel open bets af, notificeer + sluit issues.

  python wk2026_tracker.py stats
      Toon totaal stake/payout/P&L/ROI/win-rate/drawdown, beide bankroll
      modellen naast elkaar.

  python wk2026_tracker.py bankroll
      Toon huidige compound (totaal + beschikbaar) en vaste bankroll.

  python wk2026_tracker.py bets
      Lijst van alle bets (open en gesettled) met kerngegevens.

  python wk2026_tracker.py wedstrijden
      Lijst van aankomende wedstrijden uit de DB.

  python wk2026_tracker.py scrape --force
      Forceer een scrape en negeer de throttle (zie sectie 4B).

  python wk2026_tracker.py prematch
      Controleer of er wedstrijden binnen het alert-venster vallen en
      stuur (eenmalig per wedstrijd) een pre-match notificatie.

  python wk2026_tracker.py notify-test
      Stuur een testbericht via je notificatiekanaal (zie sectie 10).
      Tip: zet WK2026_NOTIFY_DRYRUN=1 om alleen te loggen zonder te sturen.

7B. DASHBOARD (dashboard.py) - LOKAAL BEKIJKEN
--------------------------------------------------------------------------------

`dashboard.py` is een interactief Streamlit-dashboard dat puur de lokale
`wk2026.db` uitleest. Het roept NOOIT The Odds API of welke externe dienst
dan ook aan - het toont alleen wat de bot al heeft verzameld. De signaal-
en Kelly-berekeningen in het dashboard spiegelen exact die in
`wk2026_tracker.py`, zodat wat je ziet overeenkomt met wat de bot doet.

Eenmalig installeren:
    pip install -r requirements-dashboard.txt

Starten (download eerst de actuele db vanaf de `data` branch, zie sectie 7
stap 6, en zet hem in deze map als wk2026.db):
    streamlit run dashboard.py
    -> opent automatisch in je browser op http://localhost:8501
    -> stoppen: Ctrl+C in de terminal

Andere database tonen:
    WK2026_DB=pad/naar/andere.db streamlit run dashboard.py

Vijf tabbladen:
  1. Signalen      - Welke wedstrijd/uitkomst zit het dichtst bij het
                     triggeren van een bet? Gesorteerd op "afstand" tot de
                     drempel. Toont actieve signalen (indien aanwezig) en
                     een staafdiagram van de grootste bewegingen.
  2. Odds-beweging - Kies een wedstrijd; zie de mediaan implied probability
                     (of decimal odd) van thuis/gelijk/uit over tijd, met
                     verticale markers op aftrap, -48u en -6u. Daaronder de
                     vroege/late beweging per uitkomst.
  3. Bets & bankroll - Tabel van alle (virtuele) bets + bankroll-curve zodra
                     er gesettelde bets zijn. Nu nog leeg (geen bets).
  4. Schema        - Volledig wedstrijdschema met status en (later) uitslag.
  5. Data & API    - Scrape-cadans per dag (doel 4/dag), aantal rijen,
                     gemiddeld aantal bookmakers, en de api_runs-log.

Top-balk toont altijd: bankroll, aantal bets, win-rate, ROI, aantal
wedstrijden en aantal scrapes. De "Ververs data"-knop in de zijbalk leegt
de cache en herleest de db (handig na het downloaden van een nieuwe versie).

De cache invalideert automatisch op de wijzigingstijd (mtime) van het
db-bestand, dus na het vervangen van wk2026.db pakt het dashboard de
nieuwe data bij de volgende rerun.

9. API BUDGET (The Odds API free tier = 500 credits/maand)
--------------------------------------------------------------------------------

  Sinds 2026-06-06 vuurt de workflow ELKE 2 UUR, maar het script throttelt
  zelf (sectie 4B). De workflow-frequentie bepaalt dus NIET het credit-
  verbruik; de throttle-gap doet dat.

  /odds endpoint
      Kost = aantal_markets * aantal_regio's = 1 * 2 = 2 credits per call.
      Bij MIN_SCRAPE_GAP_HOURS=3.5 -> ~6 echte scrapes/dag (normaal),
      plus extra in het boost-venster vlak voor aftrappen.
      Grove schatting: ~6-9 scrapes/dag * 2 = ~12-18 credits/dag
      -> ~360-540 credits/maand. LET OP: dit kan in een drukke
      groepsfase tegen de 500 aanlopen.

  /scores endpoint
      Smart-skip: alleen als er een open bet is op een wedstrijd die >2u
      geleden begon. Geschat ~30-120 credits/maand.

  Als je tegen het plafond aanloopt (check de api_runs-tabel / dashboard):
    - Verhoog WK2026_MIN_SCRAPE_GAP_HOURS (bv. 5) -> minder scrapes.
    - Verklein WK2026_SCRAPE_BOOST_WINDOW_HOURS of verhoog de boost-gap.
    - Beperk REGIO tot 'eu' (1 credit/odds-call -> halveert verbruik).
    - Of upgrade naar betaald plan ($30/maand voor 20k credits).

  Spanning om bewust van te zijn: het 'laat_publiek' signaal heeft >=2
  snapshots nodig in de laatste 6u voor aftrap. Daarom de boost. Een
  ruime boost = beter signaal maar meer credits. Tune naar je budget.

----- (A) PRE-MATCH WHATSAPP (via CallMeBot) -----

Doel: voor ELKE wedstrijd, kort voor aftrap, een samenvatting op je
telefoon. Eenmalig per wedstrijd (dedupe via kolom prematch_genotificeerd).

Setup (gratis, ~2 min):
  1. Sla +34 611 04 87 48 op als contact (CallMeBot).
  2. Stuur die contact in WhatsApp exact:
        I allow callmebot to send me messages
  3. Je krijgt binnen ~2 min een apikey terug.
  4. Zet in GitHub repo-secrets:
        CALLMEBOT_PHONE  = je eigen nummer met landcode (+31...)
        CALLMEBOT_APIKEY = de ontvangen key
  5. Test:  WK2026_NOTIFY_DRYRUN=1 python wk2026_tracker.py notify-test
            (logt alleen) of zonder dryrun voor een echt testbericht.

Timing: een alert gaat uit zodra de aftrap binnen PREMATCH_LEAD_HOURS (3u)
valt. Met runs elke 2u krijg je hem dus ~1-3u voor aftrap. Wil je meer
marge tegen overgeslagen runs? Verhoog LEAD (bv. 6), dan komt de alert
eerder maar mis je hem zekerder niet.

Timing: zie ook de uitleg onderaan deze sectie.

Voorbeeld-bericht (de tabel staat in WhatsApp-monospace via ``` fences,
zodat de kolommen uitlijnen op je telefoon):
   *WK alert: Ivory Coast vs Ecuador*
   Aftrap: 2026-06-14 23:00 UTC (over 2.5u)
   Odds (mediaan, 37 bookmakers):
     1 Ivory Coast: 3.63 (28%, dopen -1.4%)
     X gelijk: 2.84 (35%, dopen +2.1%)
     2 Ecuador: 2.35 (43%, dopen -1.3%)
   Verloop (mediaan-odd):
   ```
           t0    mid    now
   1     3.45   3.50   3.63
   X     3.02   3.00   2.84
   2     2.28   2.30   2.35
   ```
   t0=05-28 19h  mid=05-31 21h  now=06-05 18h
   Bot: geen bet (geen signaal boven drempel)

   (t0 = eerste scrape, mid = middelste scrape, now = laatste scrape.
    1 = thuiswinst, X = gelijk, 2 = uitwinst.)

WANNEER KRIJG JE HEM? De alert vuurt op de eerste run zodra de aftrap
binnen PREMATCH_LEAD_HOURS (3u) valt. Met runs elke 2u is dat in de

Fallback: als CALLMEBOT_* leeg is maar SMTP_USER/SMTP_PASS/NOTIFY_EMAIL

dan logt het script alleen (geen crash).

----- (B) GITHUB ISSUES -----

Eén issue per wedstrijd zodra de eerste bet wordt geplaatst:

   Titel:     BET: Spain vs Brazil - thuis @ 2.45 (vroeg_sharp)
   Labels:    bet, signal:vroeg_sharp, status:open
   Body:      details over wedstrijd, signaal, stakes (compound + vast),
              bankroll snapshot, bet-id.

Re-bets verschijnen als comment op hetzelfde issue.

Settle: wanneer de wedstrijd voltooid is, plaatst het systeem een
afsluitende comment met eindstand, payouts, P&L op beide bankroll-
modellen, en de actuele compound bankroll. Het issue wordt gesloten
en gelabeld als `result:won`, `result:lost` of `result:mixed`
(bij mix van win + verlies op re-bet).

Filters:
   open issues          = lopende posities
   closed + result:won  = winnende afgeronde matches
   closed + result:lost = verliezende afgeronde matches
   label:rebet          = matches waar een re-bet is geplaatst

12. SUBTIELE PUNTEN / GOTCHAS
--------------------------------------------------------------------------------

12.1  Sport key voor WK 2026
      Het script gebruikt 'soccer_fifa_world_cup'. The Odds API listt deze
      key meestal pas zodra het toernooi nadert. Verifieer met:
         GET https://api.the-odds-api.com/v4/sports?apiKey=<jouw_key>
      en pas WK2026_SPORT aan als de key anders blijkt.

12.2  Opening probability
      Het script behandelt zijn EERSTE eigen waarneming als opening.
      Echte opening odds (gepubliceerd weken eerder) zijn niet
      beschikbaar via de free Odds-API. Het venster <=48u tot KO is
      dus relatief, niet absoluut - werkt prima zolang we ruim van
      tevoren beginnen met scrapen.

12.3  /scores endpoint trefkans
      The Odds API geeft scores door zodra de bookmakers ze verwerken.
      Soms is dat al binnen 5 minuten na het laatste fluitsignaal, soms
      duurt het 30-60 min. De smart-skip (>2u na aanvang) compenseert
      hiervoor; in zeldzame gevallen kan een bet pas in een volgende
      cyclus afgewikkeld worden. Dat is geen probleem.

12.4  Race-conditions op de DB
      `concurrency: wk2026-bet-cycle` in de workflow zorgt dat slechts
      één run tegelijk draait. Daardoor kunnen twee runs niet
      tegelijkertijd dezelfde DB-versie pakken en overschrijven.

12.5  Quota uitgeput
      Als de API een 429/401 teruggeeft, faalt de huidige cyclus stil
      (try/except in daily-run logt het maar crasht niet). De DB
      blijft consistent; volgende cyclus probeert opnieuw.

12.6  Tijdzones
      Alles wordt opgeslagen in UTC. `aanvang` is UTC. Conversie naar
      lokale tijd doe je in de notificatie of bij stats; nu niet
      ingebouwd om dingen simpel te houden.

12.7  Tournament-strucruur (groep -> knockout)
      De huidige strategie maakt geen onderscheid tussen groepsfase
      en knockoutfase. In de knockout zit 90'/verlenging/penalty - wij
      gokken puur op 90 minuten (driewegmarkt h2h). Een 1-1 in de
      knockoutfase na 90 telt dus bij ons als `gelijkspel` ongeacht
      wat er in extra time gebeurt - dat is precies hoe de h2h-markt
      werkt bij de meeste boekmakers. Verifieer wel even op je eigen
      provider's site voordat je echt geld zou gaan inzetten.

14. SNELLE TROUBLESHOOTING
--------------------------------------------------------------------------------

  Actions run faalt op "401 Unauthorized"
      -> Check repo secrets: ODDS_API_KEY moet exact zo heten.

  Geen wedstrijden in DB na scrape
      -> Verifieer SPORT key (sectie 12.1). Soms heet de WC nog
         'soccer_world_cup' of 'soccer_fifa_world_cup_2026'.

  "Geen signalen" terwijl je beweging verwacht
      -> Eerste 1-2 scrapes hebben per definitie nog geen
         vergelijkings-historie. Wacht 1-2 cycli.
      -> Check `WK2026_THRESHOLD`: 6% is best stevig. Tijdelijk
         verlagen naar 0.04 om te zien of de logica vuurt.

  Issue wordt niet aangemaakt
      -> Check workflow `permissions: issues: write` aanwezig is.
      -> Check `GH_REPO` env var: moet `owner/repo` formaat zijn.

  DB lijkt leeg na nieuwe Actions run
      -> Workflow doet `git ls-remote --exit-code --heads origin data`
         voordat het probeert te restoren. Bij een geheel verse repo is
         de eerste run normaal: nieuwe DB, eerste push naar `data`.

  "fatal: refusing to merge unrelated histories" bij git pull origin data
      -> Niet doen. De `data` branch is opzettelijk een orphan branch
         zonder gemeenschappelijke history met `main`. Behandel hem
         als pure storage, niet als mergebare branch.
